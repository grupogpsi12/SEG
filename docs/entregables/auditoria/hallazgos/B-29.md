# B-29 · Informativa — El puerto 5000 de BunkerWeb responde en la red `app`, no solo en `bw-universe` como describe RS-19; lo protegen la lista blanca y el token
**Estado:** abierto — corregir RS-19 y la descripción de la red (documental)
**Ubicación:** docs/SRS.md RS-19 · infra/compose.yaml (`bunkerweb` está en las dos redes)
**Estándares:** OWASP A02:2025 · amenaza T20 · N-2
**DREAD inherente:** 9/2/2/9/3 = 5,0 (Medio) si la API se alcanzara con token; con la lista blanca y el token, 2,0 · **residual:** 2,0 (R y E bajan a 1: las seis combinaciones desde la red app fueron rechazadas)
**Origen:** F7-01 (`nmap -p-`) vio 5000/tcp abierto en 10.20.40.2; F7-02 lo probó.
**Evidencia:** `auditoria/evidencia/vulnerabilidades/F7-01-NMAP` y `F7-02-API-BUNKERWEB`.
**Impacto:** Desde la red `app` (10.20.40.0/24, fuera de `API_WHITELIST_IP`) las seis peticiones (sin token, token malo y token correcto, a `/instances` y `/health`) terminaron en reinicio de conexión. Desde `bw-universe` (dentro de la lista blanca) el token correcto fue procesado y el malo o ausente, rechazado (control positivo). La exposición real de la API es nula hoy, pero el SRS describe una topología distinta de la real.
**Corrección:** Corregir RS-19 («el puerto 5000 es alcanzable por TCP en `app`; solo responde dentro de `API_WHITELIST_IP` con token») o quitar a `bunkerweb` de `app` para la API con una regla de red. Lo primero es una línea; lo segundo, un cambio de topología.
**Prueba de regresión:** `auditoria/scripts/bunkerweb-api.sh` (seis rechazos y un control positivo) y el último bloque de `infra/waf/pruebas.sh`.
**Observación de primer principio:** Una defensa que depende de que dos controles (red y token) coincidan se debe describir con los dos, o el día que uno falle nadie sabrá que el otro faltaba.
**Falsabilidad:** Una petición desde `app` con el token correcto recibe una respuesta HTTP.
**Indicador temprano:** Una línea `bwapi` en el log de BunkerWeb con una IP de `10.20.40.0/24`.
**Esfuerzo / prioridad:** 0,5 h · Próximo
